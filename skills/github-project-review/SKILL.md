# GitHub 项目审查

## 目标

帮助有 Agent 协作、但不一定具备编程基础的普通用户回答以下问题：

1. 这个项目是不是真的能用？
2. 它属于什么项目形态，能给用户带来什么？
3. 综合用途、Agent 可协助程度、剩余门槛和风险，现在值不值得采用？
4. 公开证据中是否存在明显安全风险或必须进一步验证的信号？
5. 它明确支持 Windows、macOS、Linux 中的哪些平台，哪些平台只是理论可用或尚未确认？

这是项目采用决策助手，不是面向程序员的代码审计报告。Agent 在后台认真核验证据，但默认不要把核验过程、函数名、文件清单和内部架构倾倒给用户。

## 项目形态

先判断项目的主要形态，再解释平台、门槛和风险。可使用以下类别：桌面应用、命令行工具、网页/在线服务、浏览器扩展、开发库/框架、自托管服务、模板/内容资产或其他。项目同时具备多种形态时，标注一个主要形态和必要的次要形态。不同形态使用不同的采用标准：网页服务不应被要求“安装”，开发库不应只用普通用户的桌面安装标准衡量。

### Agent Skill 与 Prompt 集合

如果仓库包含大量 `SKILL.md`、Agent 插件清单或 Agent 配置文件，将它归类为 Agent Skill/指令集合，不要因为缺少传统实现代码或自动化测试就判为疑似空架子。此类项目的功能兑现度应检查：

- `SKILL.md` 是否具有有效 frontmatter、实质指令和完整工作流，而不是标题或占位模板；
- 插件或 marketplace 清单引用的 Skill 路径是否真实存在，安装入口与仓库结构是否一致；
- setup/install 类 Skill 是否清楚说明会写入哪些配置、文档或项目文件；
- Git、合并、发布、迁移、凭据、Issue tracker、外部服务等高影响 Skill 是否包含确认边界和失败处理；
- Skill 声称支持的 Agent 是原生发现、由安装器转换接入、需要手动指向文件，还是只有理论上的 Markdown 可读性。

深度审查优先读取插件清单，以及最多 3 个 setup/install 或其他高影响 Skill；发现破坏性文件操作、远程 Git 操作、凭据访问或 Agent 配置写入线索时扩展审查。关键词命中只能作为待复核线索，必须结合完整指令语境判断。

## 安全规则

默认只读取公开信息：GitHub 页面、API、README、公开文本源码、测试、Release 元数据、Issue、演示和文档。允许通过公开 API 获取审查所需的单个文本文件；这不等于克隆仓库或下载发布物。

未经用户明确确认，不得：

- 克隆仓库，下载源码归档、Release 二进制或其他发布物，安装、编译或运行目标项目；
- 安装依赖或修改系统、Codex、Claude Code、浏览器等配置；
- 登录账号、使用 Cookie/API Key、访问私有数据；采集器只有在用户明确同意并传入显式参数时才能使用环境中的 GitHub Token；
- 把项目代码或用户信息发送给第三方服务。

## 后台审查

Agent 应在后台完成以下检查，但不要默认逐项展示：

- 核心功能是否有真实代码，而不只是 README、界面或模板；
- README 的主要承诺能否在源码、测试、演示或 Release 中找到支持；
- 项目是否完整，是否存在明显占位、缺失入口或未完成流程；
- 外部服务、API、模型或下载链接是否可能失效；
- Windows、macOS、Linux 分别是否有明确支持证据，是否必须使用命令行、WSL、Homebrew、Docker、编译器或 GPU；
- 是否需要账号、付费服务、API Key、Cookie、数据库或长期后台服务；
- 采用后用户在 Agent 协助下是否真能使用，而不只是“理论上能运行”。

## 静态安全审查

默认对所有项目执行只读静态安全筛查。检查范围包括：

- 已读取的安装脚本、启动脚本、包清单、容器文件和工作流是否包含下载后直接执行、混淆命令、远程脚本管道执行或来源不明的二进制；
- 是否要求管理员/root 权限、关闭杀毒软件、防火墙或系统安全功能；
- 是否读取浏览器 Cookie、凭据、SSH 密钥、钱包、令牌或其他敏感目录，且用途是否与核心功能相符；
- 是否建立计划任务、服务、启动项、注册表持久化、浏览器扩展或长期后台监听；
- 网络访问、遥测、自动更新、上传行为及目标服务是否有清楚说明；
- Release 是否主要提供不可审计二进制，是否有校验值、签名、可复现构建或与源码对应的版本信息；
- 是否存在依赖清单、锁文件和自动更新工具；公开 GitHub Security Advisories 是否说明受影响版本与首个修复版本。除非另行执行依赖漏洞工具，不得声称已经完成全部依赖漏洞扫描；
- 必要时人工核对项目所有权、维护者、发布账户或下载域名是否出现异常变更；采集器未提供相关证据时必须写“未检查”，不得暗示已经完成。

不运行目标代码时，只能给静态风险结论。使用以下四档：

- **未发现明显风险**：在已检查的公开证据中没有发现明显恶意或高风险行为，但不等于绝对安全；
- **存在需确认项**：存在合理但敏感的权限、网络、凭据、后台服务或二进制行为，安装前需要解释或隔离验证；
- **高风险信号**：发现与功能不相称的敏感行为、混淆/远程执行、关闭安全防护、来源异常或已确认严重安全问题；
- **无法判断**：源码、发布物、依赖或关键服务不可见，证据不足。

安全结论必须标注置信度 `高/中/低`，并区分证据来源：文档说明、源码静态证据、公开安全通告、Issue 用户报告、维护者确认或 Agent 实际验证。没有安装、运行或沙箱复现时，不得写“安全”“已验证安全”或“没有任何风险”。

功能兑现度和维护状态是**入选门槛与后台证据**，不是默认的用户展示字段。项目已经通过功能兑现度和维护筛选后，不要再在主汇总表中重复展示“是否空架子”“功能兑现度等级”“最近维护日期”或“是否仍在维护”。安全结论会直接影响采用决策，因此批量主表可以保留一列简短安全结论；详细证据仍放在表后。只有项目被排除、结论存疑、维护情况直接改变采用建议，或用户明确要求证据时，才展开功能兑现度和维护信息。

批量比较时优先使用 `scripts/collect_github_evidence.py`。默认先用 `--mode quick` 快审最多 5 个项目，再用 `--mode deep` 深审排名前 3 个。脚本默认 3 路并发、共享 35 次 GitHub API 请求预算，并缓存结果；不要为了填满名额突破预算。脚本输出仅供 Agent 判断，不直接展示给用户。脚本中的路径名和文件名命中只是“待复核线索”，不能单独作为风险证据；必须读取相关文件或官方说明后再判断。

## 审查层级

### 快速审查

用于候选收敛，最多 5 个项目。读取仓库元数据、README 正文、最新 Release、最新提交和公开安全通告，并结合 finder 已提供的搜索证据判断用途、维护、平台兼容性、费用、基础功能兑现度和明显安全风险。不读取完整文件树，不逐个扫描安装脚本。

快速审查只需要给出可比较的短结论和排序，不要假装已经完成源码级安全审查。存在以下任一情况时，提高深审优先级：结论接近、需要敏感权限、涉及 Cookie/凭据、主要依赖二进制、安装链路复杂或安全证据不足。

### 深度审查

默认只对快速审查前 3 个项目执行。补充文件树、Release 资产、关键实现证据以及最多 3 个优先级最高的安装/启动脚本、包清单、容器文件或工作流。初始文件出现风险模式时自动扩展到最多 8 个；关键文件仍未覆盖或用户明确要求时，可通过独立扫描参数调整上限。刷新缓存不得改变扫描深度。

### 采用前完整审查

只针对用户最终选择并准备采用的 1 个项目。此阶段重新确认最新版本与提交、发布物来源和校验信息、权限与持久化行为、依赖风险、卸载与隔离验证方案。项目需要本地安装时，未经用户确认仍不得下载、安装或运行。

缓存规则：可变化的元数据默认缓存 24 小时；深度源码证据按最新提交 SHA 复用。缓存命中时注明检查时间；用户要求“最新”“重新检查”或证据已过期时绕过缓存。

## 功能兑现度等级

- **功能真实**：核心承诺有实现代码支持，并有测试、Release、演示或实际使用证据。
- **部分可用**：有真实代码，但关键功能不完整或只适用于有限场景。
- **疑似空架子**：主要是展示、模板、概念或占位，核心承诺缺少实现。
- **无法确认**：公开信息不足或关键能力依赖不可见服务。

不要因为星标、Fork、提交数量或漂亮界面就判断项目可用。证据不足时明确写“无法确认”。

## 采用建议

默认假设用户有 Agent 协作。不要因为命令行、编译、配置文件或维护步骤本身就降低采用建议；应分别说明哪些工作可以交给 Agent，哪些限制仍需要用户承担。只有凭据与隐私、付费服务、管理员权限、GPU/专用硬件、长期后台服务、不可审计二进制或法律/合规要求等不能由 Agent 消除的约束，才应明显降低采用建议。结合用户当前平台给出以下五档之一。用户未说明平台时，分别陈述 Windows、macOS、Linux 的明确支持情况，不擅自选择默认系统：

- **推荐采用**：功能真实、用途清楚，目标平台有明确支持，Agent 能处理主要技术步骤，剩余约束合理。
- **按需采用**：功能真实，但只有明确需要某种能力时才值得采用。
- **暂不建议采用**：项目可能有用，但不可由 Agent 消除的门槛、成熟度或维护成本高于预期收益。
- **不建议采用**：疑似空架子、风险明显、关键服务失效，或实际能力远低于宣传。
- **无法判断**：证据不足，不能负责任地给出采用建议。

“功能真实”不等于“值得采用”。一个项目即使代码完整，如果只是开发框架、记录模板、命令行基础设施或需要长期维护，也应结合用户是否确实需要它，以及 Agent 能否承担维护工作来判断，而不是仅因技术形态就降低评价。

平台兼容性使用以下口径：

- **明确支持**：官方文档、安装说明、Release 资产、CI 或维护者说明直接覆盖该平台；
- **可能支持**：技术栈看起来可跨平台，但缺少该平台的明确安装或验证证据；
- **明确不支持**：文档或实现明确排除该平台，或依赖该平台不存在的系统能力；
- **无法确认**：公开证据不足。README 中出现平台名称或 Release 文件名命中只能作为线索，不能单独证明完整支持。

平台兼容性默认留在后台。Windows 与 macOS 都能正常采用、操作系统不会改变建议时，不要输出平台信息；只有存在不支持、额外门槛或明显差异时才说明。

如果不知道用户的具体用途，不要追问用途。直接说明项目的通用作用、适用场景和限制，并用一句条件说明：**只有当你需要……时，它才值得采用。** 由用户自行判断是否适合。

## 默认输出

### 单个项目

默认只输出与用户采用决策直接相关的内容，控制在约 5 至 10 行，不使用超过 6 列的表格。项目形态和平台兼容性作为后台判断；除非它们改变采用建议或用户主动询问，否则不要单独显示。

```markdown
## 结论

**采用建议：推荐采用 / 按需采用 / 暂不建议采用 / 不建议采用 / 无法判断**

### 它能帮你做什么
一句话说明它是什么，以及它解决什么实际问题。必要时把项目形态自然地写进这句话，不单独列字段。

### 对你是否有用
直接说明适合什么需求；不知道具体用途时，用通用条件句表达。

### 最大风险
只保留一个最影响采用决定的风险。先用普通用户能理解的话说明“可能发生什么”，再给一句最小处理建议。不要默认展示命令、源码路径、脚本名、权限术语或内部机制；确实必须出现技术词时，立即用大白话解释。

**建议做法：**一句话说明用户现在应该怎么选、怎么避免这个风险。

**功能兑现度：功能真实 / 部分可用 / 疑似空架子 / 无法确认（置信度：高/中/低）**

**静态安全：未发现明显风险 / 存在需确认项 / 高风险信号 / 无法判断（置信度：高/中/低）**
```

“功能兑现度”一行不是固定字段。仅在用户明确询问项目是否真实/是否空架子，或结论为“部分可用、疑似空架子、无法确认”时显示；已经确认功能真实且用户只关心是否值得采用时省略。“静态安全”在用户询问安全、结论不是“未发现明显风险”、或安全结论改变采用建议时显示；显示时必须附上“静态筛查不等于绝对安全”的短说明。

证据来源默认通过引用体现，不要把“公开 Issue、静态证据、维护者确认”等审计术语塞进正文。用户要求依据或结论存在争议时，再展开证据性质。

默认不再拆出“为什么”“你需要知道”“适合什么情况”三个独立长段；相关内容分别合并到“对你是否有用”和“最大风险”。

涉及当前版本、平台支持、维护状态或 Issue 时，附上对应公开来源。具体版本、故障和维护状态必须使用绝对日期或明确版本号。维护日期默认留在后台；只有它构成风险、排除理由或用户主动要求时才展示。

公开安全通告默认是历史记录。只有当受影响版本范围覆盖用户准备采用的版本，或尚无修复版本时，才能把它写成当前采用风险；如果无法完成版本比较，写“需要确认当前版本是否受影响”，不要仅凭存在历史通告就降低采用建议。

### 风险证据口径

- GitHub Issue 中的个人报告只能表述为“有用户反馈”或“存在报告”，不能直接写成所有用户都会遇到的已确认故障。
- 只有维护者确认、已合并修复说明或 Agent 实际复现，才可使用“已确认问题”或“已验证问题”。
- 如果证据来源混合，优先说明最保守的确定性，不夸大风险。

不要默认输出：

- 源码文件路径、函数名和类名；
- 完整命令列表；
- 文件数量、提交哈希或逐个 Release；
- 状态枚举、内部数据结构和架构细节；
- 大段 README 复述；
- “能做什么/不能做什么/安装流程/证据”四套重复内容。

只有当这些信息直接改变采用建议时，才用大白话提一句。

### 批量项目

先按采用建议排序，输出简表。批量项目包括只有 2 个项目的情况；不另设“一对一比较”模式，直接在同一张表中比较：

| 项目 | 它能帮你做什么 | 采用建议 | 平台与门槛 | 安全结论 | 最大问题 |
|---|---|---|---|---|---|

主汇总表只保留影响用户选择和采用决策的字段。**不要添加**“是否空架子”“功能兑现度”“最近有效维护日期”“最后提交时间”“是否仍在维护”等列；这些已经由后台筛选保证，重复展示只会增加阅读负担。安全结论保留为简短决策字段，详细信号不要塞入主表。

- 如果任务是“搜索、筛选并排名项目”，主汇总表只放通过功能兑现度与维护筛选的候选项目；被排除、停止维护或无法确认的项目放到表后，用一句话说明排除原因，不参与排名。
- 如果用户提供固定项目清单并要求逐个审查，可以保留所有项目，但仍不单设功能兑现度或维护日期列；相关问题只在“最大问题”或表后结论中说明一次。
- 只有用户明确指定这些列，或要求审计维护证据时，才在证据表中展示功能兑现度与绝对日期；不要把证据表和面向用户的主汇总表混为一张表。

表后只补充：

- 最值得采用的 1 至 3 个项目及原因；
- 明确不建议采用的项目及原因；
- 无法判断、需要补充信息的项目。

不要默认逐个写长篇报告。finder 发起的分层交接中，快速审查只返回结构化短结论；只有排名前 3 个进入详细版。用户指定某个项目或要求“展开证据”时，再提供该项目的详细证据。

## 证据展开模式

在以下任一情况启用：

- 用户提出“详细分析、给我依据、你确定吗、展开技术证据、做代码审查”；
- “GitHub 项目寻找”（`github-project-finder`）Skill 明确把快速审查后的前 3 个项目交给本 Skill 深审。

由 finder 调用时服从交接中的 `mode`：`quick` 不进入详细模式，`deep` 才进入详细模式。不要再次要求用户确认或说“展开证据”。审查完成后，将结构化结论交回 finder，由它统一排序并生成最终报告。

详细版可以补充：

- README 与实现是否一致；
- 关键源码和测试证据；
- Release、演示和维护状态；
- Windows、macOS、Linux 的支持证据、依赖差异与潜在安装问题；
- 安装链路、权限、凭据、网络、持久化、二进制和依赖风险；
- GitHub Security Advisories、CVE 或公开安全 Issue 的证据强度；
- 尚未验证的部分。

详细模式中的功能兑现度与维护记录用于解释结论，不自动进入最终排名汇总表。对已经通过筛选的项目，不要逐项重复写“不是空架子”或罗列最近提交日期；集中说明筛选标准已经执行即可。

即使进入详细模式，也先给简短采用结论，再提供证据。技术词第一次出现时用一句大白话解释。

## 本地安装前确认

如果项目需要本地安装且采用建议为“推荐采用”或“按需采用”，先只给安装计划，不执行。计划需说明：

- 会安装什么；
- 是否需要管理员权限；
- 是否需要账号、密钥、Cookie 或付费服务；
- 会改动哪些目录或配置；
- 主要风险和卸载方式；
- 建议的低风险验证方式，例如校验发布物、Windows Sandbox、macOS 虚拟机、通用虚拟机或受限权限试运行；这些验证仍需用户另行确认后才能执行。

等待用户明确确认后才能执行。

## 失败处理

- 无法访问仓库、API 限流或关键代码不可见时，降低置信度并写“无法确认”。
- 不要为了补足证据而运行不受信任代码。
- 使用绝对日期记录检查时间，但默认只显示日期，不展示冗长元数据。
