# 审查结论校准

在形成最终采用建议前读取本文件。它用于校准证据权重、风险排序和结论措辞，不替代对当前仓库的事实核验。

## 形态权重

### 桌面应用

- 核心：可获得且来源可信的安装物、目标平台支持、主要界面流程、数据存储、更新与卸载。
- 高影响：签名或校验、管理员权限、后台常驻、遥测、不可审计二进制。
- 弱相关：是否提供开发库式 API、是否有大量单元测试。

### 命令行工具

- 核心：真实入口、主要命令闭环、依赖与运行时、输入输出、错误处理。
- 高影响：凭据、破坏性文件操作、远程执行、平台 shell 差异。
- 弱相关：没有 GUI、没有桌面安装包。

### 网页或在线服务

- 核心：服务是否可访问、核心工作流、账号与费用、数据用途、导出或退出机制。
- 高影响：隐私、数据上传、服务锁定、关键能力依赖不可见后端。
- 弱相关：没有本地安装包、仓库缺少客户端之外的不可见服务源码本身；后者应记为证据缺口而不是直接判空架子。

### 浏览器扩展

- 核心：扩展权限与功能是否相称、商店或安装来源、更新发布者、目标浏览器支持。
- 高影响：读取全部网页、Cookie、剪贴板、下载或代理权限，以及源码与发布包是否对应。
- 弱相关：没有独立桌面应用。

### 开发库或框架

- 核心：公开 API、包发布或可引用入口、文档示例、兼容版本、测试或真实采用证据。
- 高影响：维护中断导致兼容性或安全问题、供应链和依赖风险、破坏性升级。
- 弱相关：没有 GUI、普通用户不能双击安装。没有 Release 只有在分发路径依赖 Release 时才重要。

### 自托管服务

- 核心：部署入口、数据库与存储、配置、升级、备份、恢复、资源需求。
- 高影响：长期后台服务、公开网络暴露、密钥管理、数据迁移和运维负担。
- 弱相关：命令行步骤本身；Agent 能承担的常规配置不应自动降低建议。

### Agent Skill 或指令集合

- 核心：有效 frontmatter、实质工作流、引用路径真实、安装入口一致、触发范围、输出约束。
- 高影响：远程 Git、删除或覆盖文件、凭据访问、配置写入、发布和安装行为是否有确认边界与失败处理。
- 辅助：采集器或脚本测试、示例、Agent 原生清单、跨 Agent 接入说明。
- 弱相关：没有传统应用代码、没有 Release、没有安装包、仓库较新、星标少。除非这些信号直接破坏安装或更新路径，否则不得据此降低功能兑现度或作为最大风险。

### 模板或内容资产

- 核心：承诺的模板或素材真实存在、结构完整、可复用、许可证清楚。
- 高影响：素材版权、隐含外部依赖、关键文件缺失。
- 弱相关：没有运行时代码或自动化测试。

## 风险选择

按以下顺序选择最终“最大风险”：

1. 已确认的阻断风险；
2. 已确认或证据充分的实质约束；
3. 覆盖核心功能或安全边界的证据缺口；
4. 已经实质影响核心流程的工程质量问题。

若只剩普通工程质量问题，输出“主要不足”，并说明它是否影响当前采用。不要让小问题盖过项目的主要用途与真实价值。

## 回归案例

<!-- case: agent-skill-complete-no-release -->
### 案例一：完整 Agent Skill，没有 Release

事实：`SKILL.md`、清单和引用文件完整；高影响操作有确认边界；采集脚本与测试存在；用户明确需要该 Skill 的核心能力；仓库较新且没有 Release。

预期：功能真实；推荐采用；没有 Release 只能作为工程成熟度信息，不能成为最大风险。若没有其他实质约束，应写“未发现会直接阻止采用的问题”。

<!-- case: agent-skill-noncore-cache-defect -->
### 案例二：Agent Skill 存在非核心缓存缺陷

事实：核心采集流程可用；缓存异常处理与测试不一致，但默认主流程不依赖该缓存；没有高风险权限行为。

预期：功能真实；不因缓存问题降低为部分可用；缓存问题写入“主要不足”，不能作为阻止采用的最大风险。

<!-- case: polished-readme-no-implementation -->
### 案例三：漂亮 README，没有核心实现

事实：README 承诺完整应用，但仓库只有页面截图、占位组件和计划文档，没有后端、数据流程或可用发布物。

预期：疑似空架子；不建议采用；最大风险是核心承诺缺少实现，而不是维护日期或星标数量。

<!-- case: desktop-unsafe-installer -->
### 案例四：桌面应用要求关闭安全防护

事实：只提供不可审计二进制，安装说明要求管理员权限并关闭杀毒软件，项目用途不需要这些行为。

预期：高风险信号；不建议采用；最大风险是与功能不相称的系统权限和安全防护关闭要求。

<!-- case: self-hosted-real-operations -->
### 案例五：功能真实但运维负担明显的自托管服务

事实：代码、容器部署和测试完整；需要数据库、公开端口、备份和持续升级；用户只想临时完成一次任务。

预期：功能真实；按需采用或暂不建议采用；最大限制是长期运维成本，而不是命令行或 Docker 本身。

<!-- case: library-old-but-stable -->
### 案例六：维护频率低但接口稳定的开发库

事实：多年没有功能更新，但包仍可安装，测试通过，目标运行时兼容，没有未修复安全通告，API 已稳定。

预期：不能仅凭最后提交较早判定停止维护或不建议采用；根据兼容性与替代方案给推荐采用或按需采用。

## 输出自检

提交结论前确认：

- 项目形态是否改变了证据权重；
- 最大风险是否来自阻断风险或实质约束；
- 普通工程问题是否被误写成采用风险；
- “按需采用”是否说明了真实条件，而不是回避判断；
- 推荐结论是否能由已核验事实支持。
